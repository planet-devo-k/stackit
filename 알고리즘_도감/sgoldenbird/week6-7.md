# 5.1 보안과 알고리즘

## 무결성 Integrity

- 데이터가 전송되거나 저장될 때, 중간에 누군가에 의해 위조, 변조, 삭제되지 않고 원래 그대로의 온전함을 유지하는 성질

## 인터넷에서 데이터 주고 받을 때 발생할 수 있는 대표적인 문제 4가지

- 이 문제들은 사람 사이에서만 발생하는 것이 아니라 웹사이트를 열람하는 경우에도 동일하게 발생할 수 있습니다.
- 전자 서명 기술에서 문제가 되는 공개키의 소유자를 식별할 수 없는 문제를 해결하기 위해 전자 인증서라는 기술도 사용합니다.

### 1. 도청 interception → 암호화 encryption

- 제3자가 중간에서 몰래 훔쳐보는 행위

### 2. 위장 spoofing → 메시지 인증 코드 || 전자 서명, 전자 인증서

- 제3자가 다른 사람인 척 가장하는 행위
- 피싱 사이트

### 3. 변조 falsification → 메시지 인증 코드 || 전자 서명, 전자 인증서

- 제3자가 메시지를 몰래 바꾸는 행위
- 통신 상의 장애로 데이터가 망가진 상태로 전달되는 경우도 포함

### 4. 사후 부인 repudiation → 전자 서명, 전자 인증서

- 메시지를 보낸 사람이 나중에 자신이 보낸 메시지가 아니라고 주장하는 행위

# 5.2 암호의 기본

- 암호문 ciphertext: 암호화한 데이터
- 복호화 decryption: 암호문을 원래의 데이터로 되돌리는 과정

## 암호화

데이터에 어떤 연산을 적용해서 컴퓨터가 해석할 수 없는 숫자로 변경하는 것

- 데이터에는 텍스트, 음악, 사진 등 다양한 형식이 있지만 컴퓨터 내에서는 모든 데이터가 2진수로 관리
- 이러한 데이터는 컴퓨터에게 있어 의미를 지닌 숫자들의 나열
- 암호문도 숫자의 나열이긴 하나, 컴퓨터가 해석할 수 없는 임의의 숫자로 구성

## 수치계산

- 글자나 키를 (즉, 모든 데이터) 0과 1이라는 숫자로 바꾼 뒤, 컴퓨터가 비트 단위로 대조하고 연산(XOR 등)하여 값을 뒤섞거나 다시 되돌리는 과정
- 암호화의 수치 계산에서는 키를 이용하지만, 키도 숫자로 만들어집니다.
  - XOR 연산(배타적 논리합): 두 숫자가 같으면 0, 다르면 1이 되는 연산. 암호화 복호화에 가장 흔하게 쓰이는 대표적인 수치 계산

# 5.3 해시함수

- 해시함수: 주어진 데이터를 고정 길이의 불규칙한 숫자로 변환하는 함수
- 해시값: 변환된 불규칙한 숫자. 해시값은 16진수(0~9, a~f)로 표기하는 경우가 많다. 해시값도 데이터의 일종이므로 표기는 16진수로 하지만 내부에서는 2진수로 관리된다.
- 참고) 해시테이블
  - 해시테이블은 데이터를 배열 형태로 저장
  - 해시 함수는 입력된 키 값을 받아 배열의 인덱스로 변환
  - 해시테이블의 키 데이터(문자열, 파일, 아주 큰 숫자 등) 크기와 형태가 제각각 → 해시 함수는 무한한 종류의 키들을 해시테이블이 준비한 한정된 크기인 배열 인덱스로 압축, 변환하는 역할

## 해시함수의 특징

1. 데이터 크기에의해 해시값 길이가 바뀌지 않는다. 어떤 크기의 데이터를 넣든 항상 고정된 길이의 해시값이 나온다.
2. 같은 입력에 대해서는 항상 같은 출력을 제공한다.
3. 입력의 작은 변화에도 출력이 크게 달라진다.
4. 전혀 다른 데이터를 입력해도 드물지만 같은 해시값이 나올 수 있다. (해시값 충돌 collision)
5. 해시값으로부터 원 데이터를 역산하는 것이 사실상 불가능하다. 데이터 입력과 출력의 흐름이 단방향. 이것이 암호화와 크게 다른점
6. 해시값을 결정하는 계산이 비교적 간단하다.

## 암호화 vs 해시함수

### 암호화 (Encryption) -> 양방향

- 암호화는 데이터를 안전하게 전송하고, 나중에 원래대로 되돌려 읽기 위해 사용합니다.
- 방향성: 양방향
- 작동 방식: 평문(원본)을 알아볼 수 없는 암호문으로 바꾸는 과정(암호화)이 있으면, 비밀키를 가진 사람이 이를 다시 원래대로 되돌리는 과정(복호화)이 반드시 존재합니다.

### 해시 함수 (Hash Function) -> 단방향

- 해시 함수는 데이터의 고유한 특징을 추출해 내는 일종의 디지털 지문 역할을 합니다.
- 방향성: 단방향
- 작동 방식: 이미지의 다섯 번째 특징에 밑줄이 쳐진 것처럼, 결과물(해시값)을 가지고 원래 무엇을 입력했는지 역산하는 것이 수학적으로 불가능합니다.
- 사용 목적: 비밀번호를 저장할 때. 식별자.
  - 우리가 웹사이트에 회원가입을 하고 비밀번호를 설정할 때, 서버는 우리가 입력한 비밀번호(예: myPassword123)를 그대로 저장하지 않습니다.
  - 만약 그대로 저장했다가 서버가 해킹당하면 모든 사용자의 비밀번호가 그대로 유출되기 때문입니다.
  - 그래서 서버는 비밀번호를 해시 함수에 넣어서 나온 결과물(해시값)만 데이터베이스에 저장합니다.
  - 사용자가 로그인할 때: 입력한 비밀번호를 다시 해시 함수로 돌려서, 데이터베이스에 저장된 해시값과 일치하는지만 확인합니다.
  - 해커가 서버를 해킹했을 때: 해시값만 손에 쥐게 됩니다. 앞서 설명해 드린 것처럼 해시 함수는 단방향이라 역산이 불가능하므로, 해커는 해시값을 보고도 원래 비밀번호가 무엇인지 알아낼 수 없습니다.

### 해시 함수의 알고리즘

- SHA-2 등
- 알고리즘에 따라 계산 방법이 다르지만 예를 들어 SHA-1은 데이터에 덧셈이나 시프트 연산 등을 수백회 반복해서 해시값 생성.
- 알고리즘이 달라지면 같은 데이터를 입력해도 해시값이 다르다.

# 5.4 데이터를 암호화 하는 방식1: 공통키 암호 방식

암호화와 복호화에 같은 키를 사용

- 대칭형 암호 방식, 비밀키 암호 방식, 공유키 암호 방식 등으로도 불린다.
- 시저암호(Caesar cipher), AES(Advanced Encryption Standard), DES(Data Encryption Standard), OTP 등이 대표적인 공통키 암호 방식
  - 시저 암호: 알파벳 글자를 고정된 크기만큼 뒤로 밀어서 글자를 바꾸는 방식
  - DES: 1970년대에 미국 정부(NIST)가 국가 표준으로 지정했던 공통키(대칭키) 암호화 알고리즘. 데이터를 64비트(정해진 크기의 블록) 단위로 쪼개고, 이를 섞고 비틀고 교체하는 과정을 16번 반복하여 암호화
  - AES: DES가 해킹 위험에 노출되자, 이를 대체하기 위해 2001년에 새로 제정된 현대의 미국 국가 표준 공통키(대칭키) 암호화 알고리즘입니다. DES보다 훨씬 복잡한 수학적 행렬 변환을 사용하며, 데이터를 격자 모양으로 배열한 뒤 가로세로로 섞고 특정한 값들과 더하는 과정을 반복. 현재 전 세계에서 가장 안전하고 널리 쓰이는 암호 표준입니다. 우리가 쓰는 금융 앱, 인터넷 보안(https://), 압축 파일 암호 걸기 등 현대 IT 보안의 대부분이 이 AES(특히 AES-256)를 기반으로 작동합니다. 현대 슈퍼컴퓨터로도 풀 수 없을 만큼 안전합니다.
  - OTP: 매번 단 한 번만 사용할 수 있는 무작위 비밀번호를 계속 새로 생성해 내는 보안 시스템. 서버와 기기가 서로 공유하고 있는 비밀 정보(키)와 현재 시각을 조합하여, 30초나 1분마다 완전히 새로운 6자리 숫자를 만들어 냅니다. 고정된 비밀번호가 없기 때문에 해커가 중간에 번호를 훔쳐보더라도 이미 사용되었거나 시간이 지나면 쓸모없어지므로, 로그인이나 금융 거래의 2차 인증용으로 아주 강력한 보안을 자랑합니다.

문제

- 키 분배 문제: 키를 안전하게 공유하는 방법이 필요하다. 키가 제3자에게 노출되면 보안이 완전히 무너진다.
- 공통키 암호 방식은 사람이 늘어나면 필요한 키의 수가 급격하게 증가한다. $n$이 사람 수일 때, 필요한 총 키의 개수는 $n(n-1)/2$개

해결방법

- 키 교환 프로토콜 사용 (디피-헬먼 알고리즘)
  - 두 사람이 인터넷 같은 공개된 공간에서 암호화에 사용할 '공통키'를 안전하게 나누어 가지기 위한 통신 규칙
  - https:// 는 TLS(과거에는 SSL이라고 불렸던 기술)라는 보안 프로토콜을 사용하고 있다는 뜻
  - 이 TLS 안에는 안전한 통신을 하기 위해 여러 단계의 기술이 들어가는데, 그중 첫 번째 단계가 바로 서로 비밀키를 안전하게 나누어 갖는 단계(키 교환)입니다. 이때 전 세계 웹사이트들이 가장 많이 선택해서 사용하는 수학 공식이 바로 디피-헬먼 알고리즘입니다.
- 공개키 암호 방식

# 5.5 데이터를 암호화 하는 방식2: 공개키 암호 방식

암호화와 복호화에 다른 키를 사용

- 비대칭 암호 등으로 불린다.
- 암호화에 사용하는 키: 공개키 (public key)
- 복호화에 사용하는 키: 비밀키 (secret key)
- 공개키 암호의 구체적인 알고리즘으로는 RSA암호, 타원곡선 암호 등
- 불특정 다수 간 데이터 교환이 쉽다.

공개키로는 암호문을 복호화 할 수 없으므로 제3자 X는 원 데이터를 얻을 수 없다.

- 데이터를 전달받는 사람 B가 공개키와 비밀키를 만든다.
- 그 중 공개키를 A에게 전송
- A는 받은 공개키를 사용해 데이터를 암호화
- A는 암호문을 B에게 전송. B는 받은 암호문을 비밀키를 사용해 복호화

문제

- 공개키의 신뢰도에 관한 문제: 공개키 자체에는 누가 작성한지 표시하는 수단이 없다.
- man in the middle 공격: 도중에 공개키를 바꿔치기해서 데이터를 가로채는 기법
  - X가 공개키를 자신이 만든 키로 바꾸고 A에게 전달할 수 있다.
  - A는 가짜 공개키로 데이터를 암호화하고 X가 이를 가로챈다.
  - X가 B의 공개키인 원 공개키로 가짜 데이터를 암호화 한 후 B에게 전달
- 암호화, 복호화에 시간이 오래 걸린다. 따라서 상세한 데이터를 연속적으로 교환하는 구조에는 적합하지 않다.

해결방법

- 전자 인증서: 공개키의 신뢰도에 관한 문제는 공개키 작성자를 명확히
- 하이브리드 암호 방식: 암호화, 복호화에 시간이 오래 걸리는 문제 해결

RSA 암호 등 구체적인 공개키 암호 방식을 구현하는 알고리즘이 고안된 것은 인터넷 보안에서 큰 의미

- 공개키 암호 방식을 구현하는 알고리즘을 찾는건 아래 사항들을 모두 만족해야 하므로 쉽지 않다.

1. 특정 숫자를 사용해 암호화
2. 다른 숫자를 사용해 원 데이터로 복원화
3. 한쪽 키에서 다른쪽 키를 추측할 수 없는 연산

- RSA 암호 (Rivest-Shamir-Adleman)
  - 이용하는 수학적 난제: 소인수분해의 어려움
  - 작동 원리: 아주 커다란 두 개의 소수(예: 매우 큰 소수 $p$와 $q$)를 곱하는 것은 컴퓨터로도 순식간에 계산할 수 있습니다. 하지만 반대로 그 거대한 곱셈 결과값(예: 310자리 숫자)만 덩그러니 주고 "이게 어떤 두 소수의 곱으로 만들어졌는지 맞춰봐"라고 하면, 현대 최고의 슈퍼컴퓨터로 수백 년을 돌려도 소인수분해를 할 수 없습니다. 이 성질을 이용해 곱한 결과는 공개키(공개)로 만들고, 원래의 두 소수는 개인키(비밀)로 삼습니다.
  - 특징: 오랫동안 전 세계 전자상거래, 인증서, 보안 통신의 표준으로 군비해 왔습니다. 다만 보안을 강화하기 위해 숫자가 점점 커지다 보니 컴퓨터가 계산해야 할 양이 너무 많아져 속도가 느리다는 단점이 있습니다.
- 타원곡선 암호 (ECC, Elliptic Curve Cryptography)
  - RSA의 느린 속도와 큰 키 용량 문제를 해결하기 위해 등장한 차세대 공개키 암호 알고리즘입니다.
  - 이용하는 수학적 난제: 타원곡선 위의 이산대수 문제
  - 작동 원리: 특이한 대칭 모양을 가진 수학 공식인 '타원곡선'을 사용합니다. 이 곡선 위에 한 점을 잡고 특정한 규칙에 따라 튕기며 다음 점을 찾아가는 과정을 수억 번 반복합니다. 시작점과 최종 도착점은 공개되지만, 컴퓨터로도 "최종 점에 도달하기 위해 도대체 몇 번을 튕겼는가?"를 알아내는 것은 수학적으로 불가능에 가깝습니다. 이 튕긴 횟수를 개인키로 사용합니다.
  - 특징: RSA보다 훨씬 적은 자릿수(짧은 키 길이)로도 똑같이 강력한 보안을 자랑합니다. 키가 짧다 보니 계산 속도가 엄청나게 빠르고 스마트폰이나 배터리가 작은 IoT 기기에서도 부담 없이 돌아갑니다.

# 5.6 하이브리드 암호 방식

키 안전 교환(공통키의 키 분배 문제 해결) + 암호화와 복호화 처리 속도 개선(공개키의 느린 암호화, 복호화 처리 속도 해결)

- 암호화: 처리 속도가 빠른 공통키 암호화 방식
- 키: 키 분배가 불필요한 공개키 암호 방식(공개키, 비밀키)

## 과정

- A는 B에게서 받은 공개키를 사용해 암호화에 사용할 공통키를 암호화한다. 즉, 공개키로 공통키를 암호화. (p138)
- A는 암호화한 공통키를 B에게 전달
- B는 비밀키로 공통키의 암호문을 복호화. 즉, 공통키를 복호화.
- 공통키로 암호화한 데이터 전송, 복호화

## TLS에서의 하이브리드 작동 메커니즘

하이브리드 암호 방식은 인터넷상에서 정보를 안전하게 교환하기 위한 프로토콜인 SSL에서 사용되고 있다.

- SSL(Secure Sockets Layer)은 현재 업그레이드 되어 TLS(Transport Layer Security)
  TLS는 공개키 방식을 통해 대칭키를 안전하게 공유하고, 이후 실제 통신은 대칭키 방식을 사용하여 보안성과 성능(속도)을 모두 확보하고 있습니다.
  우리가 매일 사용하는 HTTPS 웹사이트가 바로 이 원리로 작동합니다.

- TLS 통신은 크게 Handshake(연결 설정) 단계와 Session(데이터 전송) 단계로 나뉩니다.
  1. 키 교환 및 인증 (공개키 방식 사용)
  - 클라이언트와 서버가 처음 연결될 때, 서로 신원을 확인하고 비밀리에 키를 나누기 위해 공개키 암호 방식을 사용합니다.
  - 서버는 자신의 인증서와 함께 공개키를 클라이언트에게 보냅니다.
  - 클라이언트는 인증서를 검증한 후, 앞으로 실제 데이터 암호화에 사용할 일회성 대칭키(세션 키)를 생성합니다.
  - 클라이언트는 이 세션 키를 서버의 공개키로 암호화하여 서버에 전송합니다.
  - 서버는 자신만 가진 개인키로 이를 복호화하여 세션 키를 획득합니다.
  2. 실제 데이터 통신 (대칭키 방식 사용)
  - 안전하게 세션 키를 공유한 후에는 속도가 빠른 대칭키 암호 방식을 사용합니다.
  - 이제 양측 모두 동일한 세션 키를 가지고 있습니다.
  - 웹페이지 데이터, 이미지, 파일 등 주고받는 모든 본문 데이터는 이 세션 키로 암호화되어 고속으로 전송됩니다.
  - 통신이 종료되면 이 세션 키는 파기됩니다.

# 5.7 디피-헬만 키 교환법

비밀의 수를 공개된 수와 연산 → 공통키를 안전하게 교환 (실제로는 키를 교환하는 것이 아니라 생성하는 것)

## 키 합성 방식의 3가지 특성

1. 키P와 그것을 이용해 합성한 키 P-S가 있다고 해도 키 S를 추출하는 것은 불가능 하다. 즉, 키를 합성할 수는 있지만 분해할 수는 없다.
2. 합성된 키를 다시 새로운 키와 합성 할 수 있다. P-P-S
3. 키의 합성 결과는 순서에 상관없으며 어떤 키를 사용했는지가 중요하다. A-B-C === B-A-C

## 과정

1. A가 B에게 키 P를 전달한다. (키 P는 제3자가 알아도 상관없다.)
2. A와 B는 각각 비밀키 SA와 SB를 준비한다. (SA, SB는 제3자가 모르게 관리)
3. A는 P+SA = P-SA , B는 P+SB = P-SB 합성
4. A가 B에게 P-SA 를 보내고 B는 A에게 P-SB를 보낸다.
   - 4-1. → X가 훔쳐볼 가능성. 하지만 키는 분해할 수 없으므로 비밀키 SA, SB를 얻을 수 없고, P-SA-SB를 합성할 수 없다.
5. SA-P-SB === P-SA-SB (합성은 순서에 의존하지 않으므로) A, B 모두 동일한 키 P-SA-SB를 가지게 된다.
6. P-SA-SB 키를 암호키, 복호키로 사용.

## 수식으로 표현한 과정

키 P는 P와 G 두개의 정수로 표현된다.

1. 키 P = P(매우 큰 소수), G(소수 P에 대응하는 생성자 중 하나)
2. A가 소수 P와 생성자 G를 준비한다. (제3자에게 노출되도 괜찮다.)
3. A가 소수 P와 생성자 G를 B에게 전달
4. A와 B가 비밀값 X와 Y를 준비. 비밀값 X와 Y는 P-2보다도 작아야 한다.
5. A는 (G를 비밀값으로 제곱 G^X) mod P, B는 G^Y mod P 계산
6. G^X mod P, G^Y mod P를 서로 교환
7. 서로에게 받은 수를 자신의 비밀키로 제곱하고 mod P. (G^Y mod P)^X mod P === (G^X mod P)^Y mod P

### 생성자 (Generator 또는 원시근: primitive root)

어떤 수 G를 거듭제곱했을 때, 소수 P보다 작은 모든 양의 정수를 규칙성 없이 무작위로 다 만들어낼 수 있는 숫자를 생성자(또는 원시근)라고 부릅니다.

1. 생성자(Generator)의 직관적인 개념

- 디피-헬만 키 교환의 핵심은 "합성은 쉽지만 분해하는 것은 엄청나게 어렵다"는 1번 특성에 있습니다. 수학에서는 이를 일방향 함수(One-way Function)라고 부르는데, 소수와 거듭제곱 연산을 이용해 이 특성을 만들어냅니다. 여기서 생성자 G는 쉽게 말해 "거듭제곱을 했을 때, 소수 P 안에서 아무도 예측할 수 없는 무작위의 숫자들을 골고루 만들어내는 특별한 숫자"를 의미합니다.

2. 왜 생성자가 필요할까? (시계 산술과 규칙성)

- 컴퓨터는 무한한 숫자를 다룰 수 없기 때문에, 특정 소수 P로 나눈 나머지 공간 안에서만 계산을 돌립니다. 이를 '모듈러 연산(pmod P)' 또는 '시계 산술'이라고 합니다.
- 만약 소수 P = 7이라고 가정해 보겠습니다. 7로 나눈 나머지는 1, 2, 3, 4, 5, 6 중 하나가 됩니다.
  - 예시 A: 생성자가 아닌 숫자 (예: 2)
  - 2를 계속 거듭제곱하면서 7로 나눈 나머지를 확인해 보겠습니다.
    - $2^1 = 2 \equiv 2 \pmod 7$
    - $2^2 = 4 \equiv 4 \pmod 7$
    - $2^3 = 8 \equiv 1 \pmod 7$
    - $2^4 = 16 \equiv 2 \pmod 7$ (다시 2로 반복)
    - $2^5 = 32 \equiv 4 \pmod 7$
    - $2^6 = 64 \equiv 1 \pmod 7$
- 나머지가 [2, 4, 1] 패턴으로만 맴돌고, 3, 5, 6 같은 숫자는 절대로 나오지 않습니다. 패턴이 너무 단순해서 해커가 비밀키를 유추하기 쉽습니다.
  - 예시 B: 생성자인 숫자 (예: 3)
  - 이번에는 3을 계속 거듭제곱해 보겠습니다.
    - $3^1 = 3 \equiv 3 \pmod 7$
    - $3^2 = 9 \equiv 2 \pmod 7$
    - $3^3 = 27 \equiv 6 \pmod 7$
    - $3^4 = 81 \equiv 4 \pmod 7$
    - $3^5 = 243 \equiv 5 \pmod 7$
    - $3^6 = 729 \equiv 1 \pmod 7$
- 결과를 보면 [3, 2, 6, 4, 5, 1]로, 1부터 6까지의 모든 숫자가 중복 없이 무작위처럼 섞여서 전부 등장합니다.

3. 실제 수식 과정과의 연결

- A와 B가 공개된 수 P = 7, G = 3을 공유합니다.
- A는 자신만의 비밀키 SA = 2를 고르고, B는 비밀키 SB = 5를 고릅니다.
- A는 $3^2 \pmod 7 = 2$를 계산해 B에게 보냅니다. (이것이 P-SA)
- B는 $3^5 \pmod 7 = 5$를 계산해 A에게 보냅니다. (이것이 P-SB)

4. 이산 로그 문제(Discrete Logarithm Problem) = 이산 대수 문제

- 소수 P, 생성자 G, G의 X승 mod P로부터 X를 구하는 문제는 아직 효율적인 해법이 발견되지 않은 상태. 디피 헬만 키 교환법은 이 수학적 난제를 이용한 키 교환법.
- 제3자인 X가 통신을 훔쳐봐서 P=7, G=3, 그리고 전달된 값 2와 5를 알아냈다고 해도,
  $3^{SA} \equiv 2 \pmod 7$에서 SA가 2라는 것을 알아내기는 매우 어렵습니다.
- 숫자가 수백 자리에 달하는 거대한 소수가 되면 수학적으로 계산이 불가능해집니다. 이를 이산 로그 문제(Discrete Logarithm Problem)라고 합니다.
- 결론적으로 생성자는 비밀키를 가지고 연산을 했을 때 결과물이 완벽하게 무작위처럼 분산되도록 만들어, 해커가 거꾸로 추적하지 못하게 방어막을 쳐주는 핵심 숫자라고 이해하시면 됩니다.

# 5.8 메시지 인증코드, MAC(Message Authentication Code)

인증 + 변조 검출(변조 방지)

- 원 메시지가 상품 번호처럼 사람이 이해할 수 없는 데이터라면 복호화해도 변조된 사실을 인지하기 어렵다. 암호에서는 변조 감지가 어려우므로 메시지 인증 코드가 필요하다.

## 과정

1. 키 공유: A와 B는 암호화 키와 인증 키(MAC용 공통키)를 안전하게 나누어 가집니다. 키 분배 문제 없이 안전하게 공유했다는 전제.
2. 암호화: A는 평문 메시지를 암호화 키로 암호화하여 암호문을 만듭니다.
3. MAC 생성: A는 이 암호문과 인증 키(공통키)를 해시 함수에 넣어서 MAC을 생성합니다.
4. 전송: A는 B에게 [암호문 + MAC]을 함께 보냅니다.
5. MAC 검증 (변조 확인): B는 받은 암호문과 자신이 가진 인증 키(공통키)를 이용해 MAC을 직접 계산합니다. 그리고 A가 보낸 MAC과 일치하는지 비교합니다. 일치한다면 암호문이 오는 동안 변조되지 않았음을 확신할 수 있습니다.
   - 5.1 → 만약 제3자가 암호문을 변조했다면, B는 변조된 암호문과 MAC를 계산하고, A가 보낸 MAC와 일치하지 않는다는 것을 알 수있다. 이를 통해 B는 암호문이나 맥 또는 약쪽 모두가 변조됐을 가능성이 있다고 생각한다. B는 A에게 받은 암호문과 MAC를 파기하고 A에게 다시 전송 요청.
   - 5.2 → 만약 제3자가 암호문 뿐 아니라 MAC도 변조한다면, 제3자는 인증키를 가지고 있지 않으므로 MAC을 변조했다해도 암호문의 변조에 맞추는 것은 불가능하다.
6. 복호화: MAC 검증이 성공하여 암호문이 안전하다는 것이 증명되면, B는 암호화 키를 사용하여 암호문을 복호화하고 원래의 메시지를 얻습니다.

MAC 작성 방법: HMAC(Hash-based MAC), OMAC(One-key MAC), CMAC(Cipher-based MAC) 등

## MAC의 결점: 사후 부인 → 해결: 전자 서명

A와 B 양쪽이 메시지를 암호화해서 MAC을 계산할 수 있다. 즉, 원 메시지를 작성한 것이 A인지 B인지 증명할 수 없다.

- A 또는 B가 악의를 지니는 경우, 메시지를 보낸 후에 그건 상대방이 보낸 메시지라고 자신이 보낸 것을 사후 부인 할 수 있다.
- 예를 들어, A와 B가 비밀키 K를 공유하고 있음
  - A가 메시지 "100만원 송금"을 보내면서 MAC을 붙임
  - B는 같은 키 K로 MAC을 검증함
  - 그러면 B는: "이 메시지는 분명히 키 K를 아는 사람이 만들었다" 는 것은 알 수 있습니다.
  - 하지만 문제는 키 K를 아는 사람이 A뿐만 아니라 B도 있다는 것입니다.
  - 따라서 나중에 분쟁이 생기면 A: "내가 보낸 거 아니야. B가 직접 만들어서 나한테 뒤집어씌운 거야." 라고 주장할 수 있습니다.
  - 실제로 B도 같은 키를 알고 있으므로: A가 MAC 생성 가능, B도 MAC 생성 가능 합니다.
  - 그래서 제3자(법원, 감사자 등)가 봤을 때는 "이 MAC이 붙은 메시지를 A가 만들었는지 B가 만들었는지 구별할 방법이 없다." 는 문제가 생깁니다.
- 즉, MAC은 작성자와 검증자 모두 같은 키를 가지고 있으므로 키를 가진 사람 중 누가 MAC을 만들었는지 알 수 없다.

# 5.9 전자 서명

인증 + 변조 검출(변조 방지) + 부인 방지

- 전자 서명에서는 전송자만 작성할 수 있는 '전자 서명'이라는 데이터를 이용해서 메시지 작성자가 누구인지 식별할 수 있다.
- 공개키 암호 방식의 순서 역응용 (암호화→ 공개키 사용, 복호화→ 비밀키 사용)
  - 공개키 방식: 공개키를 사용해 누구나 데이터를 암호화할 수 있지만, 비밀키를 가진 사람만 복호화 할 수 있다.
- 비밀키를 가진 A만 암호화할 수 있지만, 공개키를 사용해 누구나 복호화 할 수 있는 암호문 작성.
  - A만 만들수 있는 암호문을 서명으로 활용.
  - 이것은 암호로서는 의미가 없으나 암호문의 작성자가 A라는 것이 보장된다.
- 전자 서명 작성은 암호문과 다른 계산 방법인 경우도 있다. 하지만 서명 작성에는 비밀키를 사용하고 서명 검증에서는 공개키를 사용한다는 점은 공통
- 모든 공개키 암호 방식이 키를 사용하는 순서를 바꿔도 같은 방식으로 동작하는 것은 아니지만 예를 들어 RSA 암호 방식은 이 성질을 만족한다.
- 공개키 암호 방식은 암호화와 복호화에 시간이 걸리므로, 계산 시간 단축을 위해 실제로는 메시지를 직접 암호화하지 않고 먼저 메시지의 해시값을 구한 후 그것을 암호화해서 서명으로 사용한다.

## 과정

1. A가 전송할 메시지와 비밀키, 공개키 준비 (메시지 전송 측이 비밀키와 공개키를 준비하는 점이 공개키 암호 방식과 다르다.)
2. B에게 공개키 전달
3. A는 비밀키를 사용해 메시지 암호화. 이것(메시지를 암호화한 것)이 전자 서명
4. A는 메시지와 전자 서명(메시지+비밀키)을 B에게 전송
5. B는 공개키를 사용해 암호문(서명)을 복호화
6. B는 복호화한 메시지와 받은 메시지가 일치하는지 확인

## 결점 → 해결: 전자 인증서

A로 가장한 제3자와 데이터를 주고 받을 가능성이 존재한다.

- 공개키가 누구 것인지 알 수 없기 때문
- 받은 공개키에는 작성자를 가리키는 정보가 하나도 포함돼 있지 않다.
- 따라서 A로 가장한 누군가가 공개키를 작성할 가능성도 있다.

# 5.10 전자 인증서

공개키의 정당성 보장(공개키가 정말로 통신하고자 하는 상대인지 보장)

- 전자 인증서를 사용하면 공개키 작성자를 확인할 수 있다.
- 인증기관: 전자 서명을 관리하기 위한 조직. 누구든 인증 기관을 만들 수 있어서 많은 기관이 존재한다. 정부나 외부 기관을 통해 감사를 받는 대기업 등 신뢰할 수 있는 기관을 이용하는 것이 안전.

## 과정

1. A는 먼저 인증기관(CA: Certification Authority)에 공개키 PA가 자신의 것임을 나타내는 인증서 발행을 의뢰한다.
2. 인증기관은 자신이 준비한 공개키 PC와 비밀키 SC를 보유하고 있다.
3. A는 공개키 PA와 메일 주소를 포함한 개인 정보를 인증 기관에 보낸다.
4. 인증기관은 받은 정보가 A라는 것을 확인한 후, 인증기관의 비밀키SC를 이용해 A의 데이터로부터 전자 서명을 작성한다.
5. 인증기관은 작성한 전자 서명과 데이터를 하나의 파일로 만들고, 이 파일을 A에게 보낸다. 이 파일이 전자 인증서가 된다.
6. A는 공개키 대신에 전자 인증서를 B에게 보낸다.
7. B는 받은 인증서에 적힌 메일 주소가 A것인지 확인하고 인증 기관의 공개키를 취득한다.
8. B는 인증서 내의 서명이 인증 기관의 것인지 검증한다. (인증서의 서명은 인증 기관의 공개키PC로만 검증할 수 있으므로)
9. 인증서가 인증 기관에서 발행된 것이고, A 것임이 확인되면 인증서에서 A의 공개키 PA를 꺼낸다. 이것으로 A가 B에게 공개키 전달 완료.
   - 9.1 → 악의를 지닌 제3자가 공개키 PX를 전달하려해도, B는 인증서로 전달되지 않는 공개키를 신뢰할 필요가 없다.
   - 9.2 → 제3자가 인증 기관에 A로 위장해 자신의 공개키를 등록하려 해도 A의 메일 주소를 소유하지 않아서 인증서를 발급받지 못한다.

## 인증 기관 트리 구조

상위의 인증 기관이 하위 인증 기관의 인증서를 작성한다. 더 큰 조직이 작은 조직의 신뢰를 담보하는 형태로 트리 구조가 형성된다.

- B가 받은 공개키 PC는 정말 인증 기관이 발급한 것일까?
  - 공개키 자체는 작성자를 확인할 수단이 없으므로 인증기관으로 위장한 제3자가 작성한 것일수도 있다. 즉, 공개키가 가진 문제가 동일하게 발생
- 이 인증 기관의 공개키 PC도 전자 인증서로 전달된다. 이 인증 기관의 인증서에는 더 상위에 있는 인증 기관이 서명한다.
- 최상위 인증서: 최상위 인증 기관(Root CA)이 스스로 인증하는 인증서

## 웹사이트와 통신할때도 전자인증서가 사용된다.

전자 인증서는 인증 기관을 통해서 공개키 작성자를 보증하는 사회적 구조이다. 이와 같은 일련의 구조를 공개키 기반(Public Key Infrastructure: PKI)이라고 한다.

- 웹사이트로부터 공개키가 붙은 전자인증서(서버 인증서)를 받으면 해당 사이트가 제3자에 의해 위장되지 않은 것을 확인할 수 있다.
- 개인의 경우 인증서는 메일 주소와 연결되지만, 서버 인증서는 도메인과 연결된다.
- 즉, 웹사이트 도메인을 관리하는 조직과 웹사이트의 내용이 담긴 서버를 관리하는 조직이 같음을 확인할 수 있다.
