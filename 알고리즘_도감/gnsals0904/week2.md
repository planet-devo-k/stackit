# 1. 데이터 구조
## 1-4 스택
- 후입선출의 자료구조
  - 먼저들어간 데이터가 아래에 쌓이기 때문에, 가장 나중에 나오게 된다.
- 스택을 배울때마다 이걸 어디에 쓰나 라는 생각이 들곤하지만.. 생각보다 굉장히 유용한 자료구조
  - dfs 등의 알고리즘에도 사용하고 프로그래밍 동작 자체가 스택을 이용하듯 동작함.
  - 재귀함수 등도 stack처럼 동작
- 스택을 구현한다고 하면 배열로 구현할까? 아니면 리스트로 구현할까?
  - 만약에 배열로 구현한다면?
    - 현재 top의 위치를 알수있도록 해주는 포인터가 필요
      - 어차피 배열.size 나 배열.length로 알 수 있지 않나?
        - 생각해보면, 그거는 총 용량이니까 현재 사이즈를 알수없음
    - 배열의 크기를 넘어갔을때가 문제가 생김
      - 배열을 처음에 10의 사이즈로 선언하고
      - 그 배열의 크기를 넘어가게되면 배열 내부 요소를 더 큰 새로운 배열로 옮겨주는 작업이 필요
    - 대신 연속적인 메모리 공간이니까 cache hit가 높을 듯
  - 그러면 리스트로 구현하면?
    - 쭉 이어붙이기만 하면 되니까 크기를 넘어갔을때 오버헤드가 없긴함.
      - 대신 리스트는 메모리 공간 내에서 연속적이지 않으니까
      - 앞과 뒤를 가리키는 포인터가 필요할테니 공간이 조금 더 필요
    - 단방향 리스트로도 스택이 구현이 될까?
      - 음... 하나를 pop 했을때 거슬러 올라가야하니까 평소 구현하는거의 반대로 구현하면 가능

## 1-5 큐
- 선입선출의 자료구조
- 먼저 들어간 데이터가 먼저 나오는 구조
- 이것도 위의 스택의 배열 / 리스트 구현의 특성을 그대로 가져갈까?
  - 배열로 구현하면?
    - 앞이 비어있을때가 문제가 될 수 있음
    - 큐니까 앞에서부터 빼게 될텐데, 배열의 앞은 비고 뒤는 꽉차게 되면 배열의 크기가 남아있는데도 못넣는 문제가 생김.
    - 하나 뺄때마다 모든 요소를 한칸씩 당겨주는건 비효율적이니까 앞을 항상 가리키도록 하는 포인터가 필요함
  - 리스트로 구현하면?
    - 이거는 똑같을 듯 함.
    - 단방향 리스트로 구현이 되나?
      - 생각해보니 스택이든 큐든 단방향 리스트로 구현이 무조건 되겠구나
      - 노드가 앞과 뒤를 관리한다고 생각하지말고, 노드는 한쪽 방향으로만 알고 있고
      - 큐나 스택이라는 객체가 따로 큐라는 객체의 가장 앞, 뒤를 계산하고 있다고 생각하면 되겠다.

## 1-6 해시테이블
- 키 값 쌍으로 이루어져 데이터를 관리함.
- 키 값을 알고 있다면 해당 키 값이 가리키는 밸류로 O(1)의 아주빠른 속도로 찾아갈 수 있음.
- key는 기본적으로 중복될 수 없음
  - 같은 key로 저장하려면 해시 충돌 문제를 해결해주어야함.
    - 이 문제를 해결해주는 여러방법이 있는데, 책에서는 연결리스트로 해결하는 방법을 소개하고 있음.
    - 이 방법이 체이닝
    - 이렇게 구현하게 되면 어쨌든, 키 값으로 value를 찾고 그 value를 전부 선형 탐색해서 내가 원하는 값이 나올때가 탐색해야함.
- java에서는 hashMap으로 구현되어 있음.
  - 해시함수를 통해 Key 값을 해시 돌리고 그 해시 값을 기반으로 저장을 해둠.
  - hashmap도 어쨌든 메모리 공간에 저장을 하니까 초기 크기를 설정해주는게 좋을테고
  - 내부 구현은 찾아보니 레드블랙트리로 구현된다고 함.
    - 이 부분이 의아한 부분인데, 레드블랙트리는 내가 이해하기로는 트리 구조로 저장할때, 한쪽으로 너무 치우치지 않도록 사용하는 자료구조로 이해하고 있었음
    - 근데 왜 해시맵의 내부 구현이 레드블랙트리일까? 심지어 맵은 데이터가 정렬될 필요도 없잖아?
      - 만약 데이터 저장시 비슷한 해쉬값이 나오도록 하는 공격을 한다면?
        - 그러면 하나의 해쉬 값에 해당하는 데이터 공간에 계속 쌓이게 될테니 비효율적이라서 최악을 막기 위해 그렇다고 함
      - 근데 해시함수가 겉보기에는 비슷한 데이터라도 아예 다른 해쉬 값이 나오도록 하는 함수 아닌가..?
        - 그렇다고 해도 최악의 경우 이런 문제가 발생할 수 있으니 이렇게 구현되는 듯 함.

## 1-7 힙
- 우선순위 큐
- 가장 작은 값을 일관되게 항상 뽑고 싶다면? 그때 우선순위 큐를 사용
- 기억으로는 구현이 참 어려웠던 자료구조
  - 데이터를 삽입 시
    - 데이터의 자리가 운좋게 이미 들어가있는 노드를 자식으로 갖지 않는 자리인 경우에는 부모 노드의 아래에 붙이면 되니까 가장 간단함
    - 하지만 넣어보니, 부모가 나보다 작다면? 자리를 교체해주어야함.
    - 책에서는 맨 아래층(depth가 큰) 왼쪽 부터 노드를 추가해주고, 부모와 비교해서 자리를 바꾸는 방식이라고 함
      - 근데 왜 이렇게 하지?
        - 맨 아래층이라는 것은 동의하지만 왼쪽...? 일 필요가 있나?
        - 생각해보자 힙이 정렬되어있는 자료구조니까.. 맨 왼쪽 아래가 가장 작은 값인가? 아니지 부모가 제일 작으니까 이것도 아닌데?
        - 그냥 구현의 편의성 때문인가?
        - 아.. 찾아보니 완전 이진 트리의 경우 왼쪽부터 채워지는게 컨벤션이라서 그렇다고 함. 그렇다면 힙의 특성 때문은 아니구나.
  - 데이터 삭제 시
    - 힙이라는 특성 상, 가장 부모의 데이터가 나가게 될테고
    - 가장 아래의 오른쪽의 데이터를 일단 부모의 자리(root)로 옮기고 정렬해주는 작업을 진행함.
      - 여기서 가장 아래의 오른쪽을 올리는 이유도 완전 이진 트리 때문인듯
- 내부적으로는 배열을 통해서 구현되고
- max heap(가장 큰 값이 높은 우선순위). min heap(가장 작은 값이 높은 우선순위) 두가지가 있음
  - 이걸 내 맘대로 바꾸고 싶다면?
    - comparator 함수를 우선순위 큐 넣을때 넣어줘도 되고
    - 아니면 comparable을 구현한 요소를 넣어줘도 되고

## 1-8. 이진 탐색 트리
- 검색 시 정말 유용해서 많이 사용되는 자료구조
- 데이터가 이미 정렬되어있는 상태이기 때문에, 검색이 굉장히 빠름
- 기본적인 아이디어는 다음과 같음
  - 수많은 데이터가 있다고 했을 때, 이미 정렬되어 있는 데이터라면
    - 이진 탐색으로 항상 절반씩 줄여서 데이터를 찾을 수 있으니
    - 데이터가 아무리 많아도 O(log n)으로 탐색이 가능함.
  - 대신 데이터를 삽입/삭제 할때 조금 느림.
- 책에 마지막 부분에 나왔듯이 이진 탐색 트리가 진가를 발휘하려면 균형이 잡혀있어야함.
- 만약에 root에 15가 들어가있는데 1, 2, 3, 4 와 같은 데이터만 들어와서 계속 왼쪽으로 쌓이게 된다면?
- 탐색 시, 계속 왼쪽으로 가게 되어서 배열을 탐색하는거랑 다를 바가 없어짐.
- 그래서 어떻게 균형을 유지하느냐가 중요함. (ex. 레드블랙트리)
